Syncflow takes a goal, uses AI to break it into small steps it calls crumbs, and hands them to you one at a time in Focus Flow. Autopilot is the feature that lets your tools do some of those steps for you.

This is how I designed an AI agent that acts on someone's personal plan without ever finishing anything behind their back, how I built it with parallel AI coding agents, and why I then moved it out of the main product.

## The design problem

An agent working through someone's plan can go wrong in three ways. It can do things it never should, like a step that involves money, health or another person. It can spend the user's money, because Syncflow runs on the user's own AI provider key. And it can do all of that quietly, while nobody is watching.

So three rules shaped everything else:

- **Autonomy is a ladder with a ceiling**, and the user decides how high each rule may climb.
- **Rules can only tighten limits**, never loosen them.
- **Trust is earned in stages**: simulate, then preview, then shadow, then act.

## The Action Ladder

Every action Autopilot can take sits on one rung:

1. **Research it.** Reads around the step and writes tips, resources and common traps. Nothing changes; you review the notes.
2. **Plan it.** Breaks the step into smaller steps you can edit or delete.
3. **Draft it.** Produces the actual thing as a draft (the email, the outline, the checklist) and attaches it. You finish it and mark it done.
4. **Work with me.** Proposes the next small move as a thread on the step and waits for you each time. This one needs a paid plan.
5. **Complete, then ask me.** Does the whole step, then stops. The step waits for you to approve, reject or edit it.
6. **Complete and decide.** On the ladder, but switched off for every plan and every setting.

The default ceiling is level 5. Nothing in Syncflow is marked done by Autopilot without a person approving it.

## Rules

A rule has four parts: **signals** (facts about a crumb, such as its duration, its type of work, or whether it needs a human), **logic** that combines them (all of, any of, none of), an **action** on the ladder, and a **scope** for where and when it applies. Each crumb is classified before any rule looks at it, and five templates, such as "Draft what a computer can do", mean nobody has to start from a blank canvas.

## Guardrails

Seven guardrails apply to every rule, whatever it says:

- **An autonomy ceiling**, capped by the account's plan. A rule can lower it, never raise it.
- **A daily action budget** of 20 actions. Refused actions aren't queued for later, every step gets one action before any step gets a second, and a separate daily token cap protects the user's provider bill.
- **Off-limits work.** Physical, financial, health and personal steps are never auto-completed, and long steps above the user's threshold are skipped.
- **Hands off work in progress.** A step you've started is off-limits, and queued work is cancelled the moment you start, finish or skip it.
- **Quiet hours.** Work waits until your active hours, so nothing runs unwatched overnight.
- **A limit on the approval queue.** When too many results are waiting for you, Autopilot pauses and nudges instead of piling up more.
- **Auto-parking.** Three failures in a row and a rule stops trying until the underlying problem is fixed.

On top of those, two kill switches: users can pause everything from the app, and I can stop Autopilot system-wide without a deploy.

## Earning trust before acting

A new rule never goes straight to real work:

1. **Test run.** Simulates two weeks against your real tasks or a sample project, using the same rule engine and guardrails as the real thing. It never calls your AI provider and never changes a task. Every row is one decision: which task, which rule, which action, where it would run, and an estimated token cost.
2. **Try it on one crumb.** One real action with your key, shown as a preview, applied to nothing.
3. **Shadow mode.** Three real days in which Autopilot records what it would have done into Activity, as things actually happen.
4. **Live**, inside every guardrail above.

Or as the docs put it: "Use Test Run while you are drawing. Use shadow before you trust it."

## Approving feels like finishing a step

Approving an Autopilot result goes through exactly the same path as finishing a step by hand: the step moves on screen immediately, the phone gives a short vibration, the last step of a plan gets confetti, and if the server call fails, everything rolls back with a message. Autopilot doesn't get its own second-class "approve" screen. Approving is how you finish.

## Work on your own machine

Some work is better done locally, coding work especially. Autopilot can hand assignments to your own machine through Syncflow's MCP server, the protocol tools like Claude Code use to call external services:

```sh
claude mcp add syncflow \
  -e SYNCFLOW_API_KEY=… \
  -e SYNCFLOW_EXECUTOR=1 \
  -- npx -y @syncflowme/mcp-server
```

It's a pull model. The local agent announces it's alive (`executor_heartbeat`), looks for work (`list_assignments`), claims it (`claim_assignment`), does it, and hands the result back (`submit_assignment_result`), or gives it up (`release_assignment`). Nothing is ever pushed into your machine, and `SYNCFLOW_EXECUTOR=1` is an explicit opt-in: without it you still get the Syncflow tools, but nothing picks up work. Connected machines show up in an Executors tab, kept current by their heartbeats.

A nice side effect: "Claude Code is online" becomes a signal a rule can use. Coding work goes to your laptop while you're at your desk, and something else happens when you're not.

## Built with parallel AI agents

Syncflow spans four repositories: the Next.js app, the API, background jobs, and shared packages that hold the automation domain. I built Autopilot in seven batches, each split across parallel AI coding agents working in their own git worktrees. Batches one to six shipped on 7 September 2026.

Two lessons came straight from that way of working:

- **"Done" isn't the same as merged.** One agent reported a 1,368-line branch as integrated. It never was merged, and only the check I run before cleaning up worktrees caught it.
- **Parallel agents have a real cost.** Four agents used up a session's usage cap in about an hour. Since then, agents commit after every verified unit of work, so hitting a limit costs as little as possible.

## What went wrong

**It worked everywhere except where users are.** The app only forwards an API call to the backend when that path prefix is in a routing map that is baked in at build time. Automations were never added to it. For about two weeks, the whole feature couldn't be reached from a browser, while every server-side check passed. The lesson: test the full path from the browser, not just the parts.

**The published package lagged behind the repo.** npm still had version 1.0.0 of the MCP server, while the repo had 1.2.0 with the executor tools. Anyone running `npx` got the old version, never sent heartbeats, and never appeared in the Executors tab. What users install is the product, not what the repo contains.

**Types that only existed inside the monorepo.** A type exported only from a submodule of a shared package typechecked fine inside the workspace and vanished from the published build. It cost one wasted release.

## Then I moved it out of the way

Autopilot is the clearest example of a mistake I've since put a rule against: building the technology first. The rule now is to start from the customer's experience and work back. The reference user is Ana, who asked ChatGPT for a plan and never finished it. Ana doesn't need an automation canvas. She needs her goal turned into a plan, and to do the next step.

In September 2026, Syncflow had 21 active accounts and €0 in revenue, built by a solo founder working about 20 hours a week. Its first month brought 500+ sign-ups, but many didn't stay active. At that stage, the first five minutes of the product matter more than any power feature.

So Autopilot came out of the main path. It's gone from the top navigation, the dashboard card and Settings, and lives in the account menu instead, where power users can reach it and first-time users never meet it. I hid it rather than deleting it: the work stays available, it's just not what Syncflow's first experience should be. That stays goal, then plan, then one step at a time.

## What I'd do differently

- **Write Ana's story before the architecture.** The guardrails and the ladder hold up. The order I built things in didn't.
- **Make "reachable from a browser, installed from npm" the first test**, not something discovered weeks later. Every server-side check passing proved nothing about what a user would actually see.
